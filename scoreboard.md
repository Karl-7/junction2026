# Scoreboard

Every result we have produced, grouped by environment version. Newer versions are at the top.
Reward is in [0, 1] and is computed server-side from the hidden state (see `hidden_element/scoring.py`).

**How the agent runs were made.** Docker was not available in the development container, so the
model runs below are *proxy runs*, not Harbor/OpenCode runs. A model was given only the task
instruction (`instruction.md`, generated by `scripts/build_tasks.py`) and a command-line MCP
client (`python -m policies.play`). It talked to a lab server running in a separate process
with a hidden seed. It was told not to read any other file. Server-side trajectories hold every
tool call, its raw response and the hidden truth. They are viewable with
`python -m scripts.show_trajectory <trajectory.json> --truth`. Official Harbor runs use
`scripts/run_harbor.sh` and will be added here once they exist.

"Reference" is `policies/reference.py`, a fixed script that uses the same MCP tools and no hidden
state. On every seed it is compared against the reference version that was current at that time.

**Failure analysis (v1)**

Each loss below is traced to one decision in the task. In every case the information the agent
needed was available through the tools.

| Decision | What the task requires | Haiku 101 | Haiku 102 | Haiku 103 |
|---|---|---|---|---|
| Deal with the interferer | Wait several half-lives (the range is public) before following activity | ✓ waited 150 h | ✓ waited 240 h | ✓ waited 200 h |
| Follow the signal through precipitations | Keep the product holding the target's activity; subtract background and the known radioactive element | ✓ | ✓ | ✓ |
| Identify the carrier | The known element whose partition matches the target on every reagent | ✓ Qu | ✓ Qe | ✓ Qy |
| Correct the atomic weight | Remove the contaminants' contribution, using the spectrum-derived fractions | ✓ within 1% | ✓ 2.2% off (98% credit) | ✓ within 1% |
| **Recover target from mother liquors** | Re-crystallise mother liquors and merge them back; otherwise each round throws away 20–50% of the target | ✗ never recycled | ✗ never recycled | ✗ re-crystallised a mother liquor but never merged it (0 `combine` calls) |
| **When to stop** | Stop when purity ≈ goal and recovery ≈ goal, using the remaining budget | ✗ stopped with 49 actions unused | ✗ stopped with 37 actions unused | ✗ stopped with 35 actions unused |

Run notes:
- **Haiku 101 (0.258).** Purity 0.607 is close to the reference's 0.630. Recovery is 0.100
  against the reference's 0.322. Every mother liquor was discarded. The model's own report names
  the cause but takes no action: "recovery is low (~0.10 against a 0.3 threshold), because each
  crystallisation step discarded ~30-50% of the target into mother liquor". It submitted with
  49 actions left, which was enough to recycle.
- **Haiku 102 (0.346).** Six crystallisations at fractions 0.5–0.6, all with the mother liquor
  discarded. Recovery was 0.134 and purity 0.612. It stopped by reasoning that "a further
  crystallisation step was not worth it, since recovery would fall faster than purity rises".
  That is correct only *if* mother liquors are discarded, and recycling is how to escape this
  trade-off. Its own reward estimate (~0.36) was close to the true 0.346, so it read the scoring
  rules correctly. The loss comes from strategy, not from misreading the task.

- **Haiku 103 (0.360).** It opened crystallisation with an extreme fraction of 0.05 (step 26),
  leaving almost all the target in mother liquor S10. It then purified the crystal branch
  (S13 → S15), *abandoned* it, and started a second chain from the old mother liquor S10
  (S17 → S19 → S21 → S23). Its report describes this as "repeated crystallisation of mother
  liquors", but the two branches were never combined, so the target ended up split across
  branches and much of it was thrown away. Recovery was 0.134 and purity 0.653. It submitted
  with 35 actions left.

The common pattern: the model treats crystallisation as a one-way chain, keeps the crystals and
throws everything else away. It never uses `combine` to bring material back. In v0b this cost
little because `recovery_goal` was 0.15. In v1 it is the dominant source of the gap.

## v0b: `default-v0` after reward-integrity fixes · commit `dfac6fd`

Changes from v0a:
- The carrier no longer leaks through the public ore assay. Before the fix it was the rarest
  element in 200 of 200 seeds; now it shares its abundance range with two other elements and is
  the rarest in 66 of 200.
- Report credit is multiplied by the recovery score, so a microscopic pure sample earns little.
- The reference uses crystal fraction 0.7 instead of 0.5.
- `recovery_goal` 0.15 and `target_alpha` 6–10 are unchanged.

because the API key's free tier allows 20 requests per day per model
(`GenerateRequestsPerDayPerProjectPerModel-FreeTier`). That is a quota limit, not model behaviour.
